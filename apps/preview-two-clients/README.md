# preview-two-clients

plan.md §3.14 が mx-multiplayer に要求する 2 本目の検証手段——**ローカル 2 クライアントのプレビュー**——である。
plan.md §6 Step 2 の完了条件は「テスト green **かつ** 内蔵プレビューが操作可能」であり、本アプリがその後半にあたる。

**これはパッケージではない。** plan.md §4.1 のとおり `apps/preview-*/` に置かれた dev アプリであり、
`index.ts` から export されず、他リポジトリから import できない。`pnpm verify` はこれを実行しない。

```console
$ pnpm preview                                  # 対話モード。SPACE で 1 ステップ進む
$ pnpm preview --list                           # ハンドシェイクの台本と、各ステップで何を見るか
$ pnpm preview --stats                          # 測定レポート（下記「見つけたもの」の出所）
$ pnpm preview --once --ascii --script          # 正常セッション 1 枚（貼り付け用）
$ pnpm preview --once --ascii --script --frames  # 生のフレームテキスト付き
$ pnpm preview --once --ascii --script --fault kill-transport --fault-at 1 --view machine
$ pnpm preview --once --ascii --script --fault future-message --fault-at 1 --view wire
```

## 何が動いているか

**1 プロセスの中に 2 つのピアがいて、`makeLoopbackPair` で互いに配線されている。**
台本は 15 ステップで、`SPACE` 1 回につき 1 ステップ進む。

- **フレームは全部本物である。** `domain/codec.ts` の `encodeFrame` を通り、
  `WireText`（文字列）としてトランスポートを渡り、`decodeFrame` で戻る。
  Port が `NetworkMessage` を運んでいたら、ループバックはオブジェクトを参照で渡すだけになり、
  コーデックのバグは 1 つも現れない（docs/testing.md §3）。だから `corrupt` フォールトが
  「フレームの真ん中の 1 文字を書き換える」という形で成立する。**書き換える対象のフレームが本当にある。**
- **状態は全部本物である。** 両ピアの遷移は `domain/connection.ts` の `transition` が返したものである。
- **このアプリが足しているのは 2 つだけ**で、どちらもこのリポジトリが**持つべきでない**もの:
  1. **セッションの台本。** `domain/connection.ts` は方針を持たない（DN-8: 「タイマーもスケジュールも
     試行回数上限も持たない」）ので、「セッションとはどういう形か」は誰かが言う必要があり、
     本番ではそれはソケットを所有するアダプタである。
  2. **フォールトインジェクタ。**

## ビュー（`v` で巡回）

| ビュー | 何を示すか |
| --- | --- |
| `wire` | フレーム 1 本 1 行。誰が送ったか / タグ / **エンベロープの `protocolVersion`** / バイト数 / 掛けたフォールト / **受け手の判定を受け手の言葉で** |
| `machine` | 両ピアの状態、`canSend()`、不正イベントの回数、そして**要求された遷移の全履歴** |
| `faults` | フォールトのメニューと、それぞれが何を突くのか |

`wire` の `v` 列を毎行出しているのは、DN-1 の主張が**バージョンはエンベロープにあるから
メッセージより先に読める**というものだからである。**読めていない**というのが F1 である。

`machine` の `REJECTED` 行が読みどころである。`transition` は不正イベントに `undefined` を返し、
モジュールヘッダは「`undefined` を受け取った呼び出し側は自分のロジックのバグを見つけたのだ」と書いている。
`--fault kill-transport --fault-at 1` を投げると、**1 本の死んだソケットに対して REJECTED が 5 行連続で出る**。
呼び出し側にバグは無い。

## フォールト

**これがこのアプリの存在理由である。** ここに並んでいるのは「テストでは到達しにくく、
本物のピア相手には手では到達できない」経路であり、DN-8 自身が
「不安定な回線でしか再現しないため、テストに乗らない」と書いている領域である。

### wire フォールト（`f` で巡回。**次の 1 フレームだけ**に掛かる）

| 名前 | 何をするか |
| --- | --- |
| `drop` | エンコードして、配送しない。**送り手は成功を見る** |
| `corrupt` | フレームテキストの真ん中 1 文字を書き換える → 受け手で `malformed-frame` |
| `wrong-version` | `PROTOCOL_VERSION + 1` でエンコード → `unsupported-protocol-version` |
| `future-message` | **新しいビルドが送ってくるであろうフレームを直に作る。** このビルドの union には無いタグを載せるので `encodeFrame` では作れない |
| `kill-transport` | 送り手のトランスポートを `disconnectedTransport` に差し替える。ハンドシェイク中に投げれば「ソケットが途中で死ぬ」 |

**一度きりなのは意図的である。** 毎フレーム壊れるプレビューは 1 つの失敗を繰り返し見せるだけで、
見たいのは「正常なセッションの真ん中に 1 本だけ悪いフレームが入ったとき何が起きるか」である。

### machine フォールト（即時。今の状態に対して撃つ）

`a` 二度目の `ConnectRequested` / `b` 状態を問わず `ConnectRequested` / `c` `RetryRequested` /
`d` `HandshakeFailed` / `e` `PeerClosed` / `w` 状態を無視して Chat を送る / `z` 300 文字の Chat を送る。

## 何が見えないか

- **ソケットは 1 つも開かない。** WebSocket も `ws` も再接続スケジュールもサーバプロセスもここには無い。
  それらは Port の上のアダプタであり、プラットフォームを持つリポジトリのものである
  （`domain/transport.ts` 冒頭、docs/testing.md §5）。
- **遅延も帯域も順序入れ替えも無い。** ループバックは同期キューである。順序保存は測定している
  （`--stats` の round-trip チェック）が、「順序が入れ替わったら」は再現していない。
  それはアダプタの性質であってプロトコルの性質ではない。
- **ゲームの状態が無い。** `BlockBreak` が届いても何も壊れない。DN-9 のとおり、
  誰が勝つかを決めるのは mc-sim と mx-gameplay であり、mx-multiplayer はその決定を**運ぶ**だけである。
- **画面が無い。** マルチプレイヤー画面は mx-ui のものである（plan.md §3.14）。

## 見つけたもの

`pnpm preview --stats` は 10 個のチェックを**実行時に測定**しており、記録された期待値は 1 つも無い。
直せば finding は自動的に消える。初回実行（2026-07-27）は 4 件だった。
**4 件すべて `test/preview-findings.test.ts` に assertion として落としてある。**
レポートは読まれなければ効かないが、テストは落ちる。

| # | 症状 | 詳細 |
| --- | --- | --- |
| **M1** | **バージョンがメッセージ形状より**後に**検査されている** | DN-1 は「バージョンはメッセージの外側に置く。内側に置くと、未知バージョンのフレームを弾くためにまず『もう存在しないかもしれないメッセージ形状』をパースする必要が生じる」と言い、`domain/protocol.ts:205-211` が繰り返している。エンベロープは確かに外側にあるが、`domain/codec.ts:89-99` は `Frame` を**まるごと**（`message: NetworkMessage` を含めて）構造デコードし、バージョン比較は `:100` の後である。結果、**新しいビルドから来たフレームは、このビルドのスキーマが受け付けない形を含んだ瞬間に `malformed-frame` になる**。実測 3/4。2 つの判定は交換可能ではない —— DN-1 は前者に「フレームを捨てる」、後者に「**ピア**を切ってユーザにそう伝える」を割り当てている。ローリングアップグレード（DN-1 が存在する唯一の理由）が「パケットが壊れています」として出る |
| **M2** | **`ConnectionState.Connecting.attempt` は常に 1** | 生成箇所は `domain/connection.ts:80` と `:116` の 2 つだけで、どちらもリテラル `1` を書く。前の attempt を読むものも増やすものも無い。7 回試行して観測値は `[1,1,1,1,1,1,1]`。このフィールドは export されており `api-lock.md` にも載っているので、mx-ui は永久に「attempt 1」を描ける。DN-8 の「試行回数**上限**を持たない」は正しい（上限は `Schedule` でアダプタのもの）が、**進行中の試行の序数**は別物で、機械が入口で上書きするのでアダプタからは供給できない |
| **M3** | **決着した接続が、実際のソケットが次に届けるイベントを拒否する** | `Closed + PeerClosed`、`Closed + TransportFailed`、`Disconnected + CloseRequested` がすべて `undefined`。しかしソケットは書き込み失敗と close を**両方**届けるし、ユーザは Disconnect を 2 回押す。`domain/connection.ts:16-21` は「`undefined` を受け取った呼び出し側は自分のロジックのバグを見つけたのだ」と書いているが、この 3 つに呼び出し側のバグは無い。**遷移の間違いではなく契約の問題**である —— 決着後はこれらを合法かつ冪等にするか、`undefined` に第 3 の意味（「もう処理済み」）を与えて全アダプタに状態フィルタを義務づけるかのどちらかで、今はドキュメントが後者を言い、コードが前者を意味している |
| **M4 (解決済み)** | **Connected-only send gate** | `connectionGatedTransport` が各 send 時に現在の `ConnectionState` を読み、`Connected` 以外を `TransportError(not-connected)` で拒否する。raw transport はハンドシェイクと後方互換性のため維持する |

**M1・M3・M4 は当初の 107 本のテストが 1 つも捕まえていなかった。** M4 は現在解決済み。理由:

- **M1** —— バージョンテストは 2 本とも**このビルドが知っているメッセージ**を v+1 で包む
  （`SAMPLES.Ping` と `SAMPLES.PlayerLeave`）。**メッセージを 1 つも変えないバージョン上げ**が
  唯一うまくいくケースであり、それは最も起こりそうにないケースである。
- **M3** —— `test/connection.test.ts` は遷移表を単体で網羅するが、
  **アダプタが実際に生む列**（書き込み失敗 → close）を 1 つも通していない。2 クライアントを回して
  トランスポートを殺すと 1 回で出る。
- **M4 (解決済み)** —— 現在は `test/transport.test.ts` が可変な状態と transport を組み合わせ、
  `Connecting` / `Connected` / `Closed` の配送境界を検査する。

合格したまま残しているチェックも 6 つある（DN-2 / DN-3 / DN-5 / DN-6 / DN-7 とラウンドトリップ）。
合格したら消すチェックは、コードを 1 回しか検査しない。
そのうち 3 つはテストにも落としてあり、**うち 2 つはこれまで assertion が無かった**:
「不正値は**送信側**で落ちる」（DN-5 の主張は `Schema.encodeEither` の性質であって、
スキーマの性質ではない）と「知らないフィールドは**無視される**」（DN-6 の前方互換の半分。
今は `Schema` の既定動作であって決定ではない）。

## 制約

- `apps` は `SCAN_ROOTS` に入っている（`scripts/check-dependency-whitelist.ts:238`）。
  したがって import は他のソースと同様にゲートされる。**新規依存は 0 個**——色ライブラリすら足していない。
  `effect` と、このリポジトリ自身のモジュールしか import しない。
- `Date.now()` / `new Date()` / `performance.now()` 禁止も適用される。
  **エスケープハッチ (`mc-kernel-allow-time-source`) は使っていない。**
  ここではそれが単なる遵守ではなく**主題**である —— DN-3 はプロトコルから壁時計を外した。
  往復時間をミリ秒で測るプレビューは、**それが消えていることを証明するはずの唯一の場所**に
  壁時計を戻すことになる。`Ping`/`Pong` は**ノンス**で対応付けており、
  ノンスはセッションが持つカウンタである。
- 型検査は `tsconfig.preview.json`（`types: ["node"]`）。
  `tsconfig.build.json` は**触っていない**——DN-4 の機械的保証
  （`lib: ["ES2024"]` / `types: []` なのでプロトコル層はプラットフォーム依存を獲得できない）はそのまま残る。
